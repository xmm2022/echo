# Echo v0.4 设计

- 日期: 2026-06-04
- 作者: Echo 项目
- 状态: 设计稿,已完成子代理审查
- 范围: 只设计 v0.4;不写实现代码

## 1. 项目定位

Echo v0.4 是建在 v0.2 用户/配额模型与 v0.3 discovery 管理层之上的用户侧媒体请求与订阅层。

一句话: **Echo 让普通用户表达“我想看什么”,由管理员策略把请求准入为 canonical discovery subscription,再复用 v0.3 scheduler / matches / producer dispatch / v0.1 ingest 完成发现与入库。**

v0.4 不是新的云盘执行面,不是新的 CAS producer,也不是把 v0.3 admin discovery routes 放开给普通用户。用户侧只接触安全 DTO、自己的请求状态和可用结果;source / producer profile / rule profile / raw debug / match accept-reject-retry 继续 admin-only。

### 设计审查记录

本 spec 的主要段落经过只读子代理 focused review,审查意见已合并:

- 架构方向: Plato
- 数据模型 / API / 状态机: Averroes
- 安全 / 隐私 / release gate: Ptolemy
- 用户体验 / 前端边界: Avicenna

### v0.4 目标

包含:

- 用户侧媒体搜索: 复用 v0.3 TMDB client/cache,只返回安全摘要。
- 用户媒体请求: 普通用户创建、取消、查看自己的 movie / tv 请求。
- 用户订阅视图: 普通用户查看自己关注的 canonical discovery subscription 状态与安全时间线。
- 管理员准入策略: admin 配置哪些用户可搜索、可请求、是否自动批准、目标 library / producer profile / rule profile。
- 管理员审核队列: admin approve / reject 用户请求;approve 后创建或复用 canonical `discovery_subscriptions`。
- 多用户同片去重: 多个用户请求同一媒体目标时复用同一个 canonical subscription,避免重复 match/dispatch/job。
- 安全 facade: 用户侧 API/UI 单独 namespace,不复用 v0.3 admin response。
- 审计与限速: 记录请求、取消、批准、拒绝、策略拒绝、限速拒绝等事件。
- 测试与 release gate: fake full path 覆盖 user request -> approval -> discovery -> producer job -> status backfill。

不包含:

- 普通用户直接创建/修改 `discovery_subscriptions`。
- 普通用户访问 source / producer profile / rule profile / candidates / matches / runs / raw debug。
- 普通用户提交 115 share、receive code、producer args、source URL 或 secret ref。
- 139 / 189pc 自动 producer。
- `cas139` Echo-side 自动化或 139 remote CAS tree import。
- `by-echo` 路径反查接口。
- WebDAV/S3 `.echo` 输出。
- 跨 hash conflict 自动 merge。
- 完整海报墙、trending 频道、推荐算法、评论、收藏、watchlist、内置播放器、通知系统。
- Telegram 登录/session 创建 UI。
- 复杂 ACL / 目录级授权 / 多人协作请求。

v0.1 主 spec 的 CAS-only、sidecar HTTP 边界、真实上传 fallback 禁止、路径安全规则全部继承。v0.2 / v0.3 已经完成的管理与 discovery 能力不回头重写。

## 2. 架构

v0.4 采用 **用户请求准入层 + 现有 discovery 内核**:

```text
+---------------------------+
| User /app                |
| - search TMDB            |
| - create request         |
| - view own status        |
+------------+-------------+
             |
             v
+---------------------------+
| v0.4 media request layer  |
| - access policies         |
| - request ledger          |
| - user subscriptions      |
| - safe DTOs               |
+------------+-------------+
             |
       approve / auto approve
             |
             v
+---------------------------+
| v0.3 discovery core       |
| - discovery_subscriptions |
| - subscription_matches    |
| - source crawl / rules    |
| - 115-only dispatch       |
+------------+-------------+
             |
             v
 ingest_producer -> 115share2cas -> v0.1 ingest -> library_entries/file_copies
```

Dependency boundary:

- `library_entries` / `file_copies` 仍只由 v0.1 ingest 写入。
- `discovered_resources` / `subscription_matches` 仍由 v0.3 discovery 写入。
- v0.4 只写用户意图、准入策略、请求事件和用户到 canonical subscription 的映射。
- 用户侧状态从 request ledger、canonical subscription、matches/job 的 redacted projection 汇总得到。

### 包结构

```text
internal/media/
  types.go              MediaRequest, AccessPolicy, UserMediaSubscription
  policy.go             resolve user policy + target
  requests.go           create/cancel/list/approve/reject request service
  subscriptions.go      user subscription projection and pause/resume intent
  dto.go                safe response DTOs

internal/http/handlers/
  media.go              /api/me/discovery/* and admin request/policy routes

internal/web/templates/
  media.templ           user-facing /app fragments
```

`internal/media` may call v0.3 `tmdb` and store queries, but must not import or expose source adapters, raw debug, producer execution internals, or sidecarclient directly.

## 3. 数据模型

SQLite remains the only committed database.

### `discovery_access_policies`

Admin-created user admission policy. Higher priority wins; `subject_user_id IS NULL` is the default policy.

```sql
CREATE TABLE discovery_access_policies (
  id                       INTEGER PRIMARY KEY AUTOINCREMENT,
  name                     TEXT NOT NULL UNIQUE,
  enabled                  INTEGER NOT NULL DEFAULT 1,
  priority                 INTEGER NOT NULL DEFAULT 100,
  subject_user_id          TEXT REFERENCES users(id),
  request_mode             TEXT NOT NULL
    CHECK (request_mode IN ('disabled','approval_required','auto_approve')),
  can_search               INTEGER NOT NULL DEFAULT 1,
  max_pending_requests     INTEGER,
  max_active_subscriptions INTEGER,
  request_cooldown_seconds INTEGER,
  created_by               TEXT REFERENCES users(id),
  created_at               INTEGER NOT NULL,
  updated_at               INTEGER NOT NULL
);
```

If no enabled policy matches, fail closed: user search and request creation are forbidden.

### `discovery_policy_targets`

Safe target choices exposed to users as labels. Users select a target label, not raw library/profile/account ids.

```sql
CREATE TABLE discovery_policy_targets (
  id                         INTEGER PRIMARY KEY AUTOINCREMENT,
  policy_id                  INTEGER NOT NULL REFERENCES discovery_access_policies(id) ON DELETE CASCADE,
  label                      TEXT NOT NULL,
  library_id                 INTEGER NOT NULL REFERENCES libraries(id),
  producer_profile_id        INTEGER NOT NULL REFERENCES discovery_producer_profiles(id),
  rule_profile_id            INTEGER NOT NULL REFERENCES rule_profiles(id),
  pipeline_owner_id          TEXT NOT NULL REFERENCES users(id) DEFAULT 'admin',
  media_type                 TEXT CHECK (media_type IS NULL OR media_type IN ('movie','tv')),
  match_mode                 TEXT NOT NULL CHECK (match_mode IN ('admin_review','auto_dispatch')),
  grant_playback_on_approval INTEGER NOT NULL DEFAULT 0,
  enabled                    INTEGER NOT NULL DEFAULT 1,
  default_target             INTEGER NOT NULL DEFAULT 0,
  created_at                 INTEGER NOT NULL,
  updated_at                 INTEGER NOT NULL,
  UNIQUE (policy_id, label)
);
```

`pipeline_owner_id` is the owner written to canonical `discovery_subscriptions`. This prevents two users requesting the same title from producing separate pipeline subscriptions only because requester ids differ.

### `discovery_subscription_requests`

User request ledger. It snapshots user-visible metadata and admin policy choices so later library/profile/title changes do not rewrite history.

```sql
CREATE TABLE discovery_subscription_requests (
  id                             INTEGER PRIMARY KEY AUTOINCREMENT,
  requester_user_id              TEXT NOT NULL REFERENCES users(id),
  status                         TEXT NOT NULL
    CHECK (status IN ('pending_review','approved','rejected','canceled','failed')),

  tmdb_id                        TEXT NOT NULL,
  media_type                     TEXT NOT NULL CHECK (media_type IN ('movie','tv')),
  tmdb_language                  TEXT NOT NULL,
  title_snapshot                 TEXT NOT NULL,
  original_title_snapshot        TEXT,
  release_year_snapshot          INTEGER,
  poster_path_snapshot           TEXT,
  season_filter_json             TEXT,

  policy_id_snapshot             INTEGER,
  policy_target_id_snapshot      INTEGER,
  target_label_snapshot          TEXT NOT NULL,
  target_library_id              INTEGER NOT NULL,
  target_library_name_snapshot   TEXT NOT NULL,
  producer_profile_id_snapshot   INTEGER NOT NULL,
  producer_profile_name_snapshot TEXT NOT NULL,
  rule_profile_id_snapshot       INTEGER NOT NULL,
  rule_profile_version_snapshot  INTEGER NOT NULL,

  user_note                      TEXT,
  admin_note                     TEXT,
  reviewed_by                    TEXT REFERENCES users(id),
  reviewed_at                    INTEGER,
  subscription_id                INTEGER REFERENCES discovery_subscriptions(id),
  idempotency_key                TEXT NOT NULL UNIQUE,
  last_error_kind                TEXT,
  last_error_message             TEXT,
  created_at                     INTEGER NOT NULL,
  updated_at                     INTEGER NOT NULL
);
```

Idempotency key:

```text
sha256(requester_user_id, tmdb_id, media_type, tmdb_language,
       policy_target_id, normalized_season_filter_json)
```

### `user_media_subscriptions`

Links users to canonical discovery subscriptions. This is the user-facing subscription object; it is distinct from the internal pipeline subscription.

```sql
CREATE TABLE user_media_subscriptions (
  id                     INTEGER PRIMARY KEY AUTOINCREMENT,
  echo_user_id            TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  request_id              INTEGER REFERENCES discovery_subscription_requests(id),
  discovery_subscription_id INTEGER NOT NULL REFERENCES discovery_subscriptions(id) ON DELETE CASCADE,
  tmdb_id                 TEXT NOT NULL,
  media_type              TEXT NOT NULL CHECK (media_type IN ('movie','tv')),
  season_filter_json      TEXT,
  season_filter_key       TEXT NOT NULL,
  status                  TEXT NOT NULL CHECK (status IN ('active','paused','canceled','completed')),
  created_at              INTEGER NOT NULL,
  updated_at              INTEGER NOT NULL,
  UNIQUE (echo_user_id, discovery_subscription_id, season_filter_key)
);
```

For TV, the canonical `discovery_subscriptions` row remains series-level under the existing unique key. User-specific season filters live in `discovery_subscription_requests` and `user_media_subscriptions`; approval may broaden the canonical `season_filter_json` by policy-controlled union, but must not create duplicate canonical rows for the same `(tmdb_id, media_type, pipeline_owner_id, library_id)`.

`season_filter_key` is the stable normalized key for uniqueness: empty string for all seasons, otherwise `sha256(normalized_season_filter_json)`.

### `discovery_subscription_request_events`

Append-only audit trail.

```sql
CREATE TABLE discovery_subscription_request_events (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  request_id    INTEGER NOT NULL REFERENCES discovery_subscription_requests(id) ON DELETE CASCADE,
  actor_user_id TEXT REFERENCES users(id),
  action        TEXT NOT NULL,
  from_status   TEXT,
  to_status     TEXT,
  note          TEXT,
  snapshot_json TEXT NOT NULL DEFAULT '{}',
  created_at    INTEGER NOT NULL
);
```

Events must not contain raw share URLs, receive codes, secret refs, producer args, raw Telegram text, or job payloads.

## 4. API 与 UI

### 用户 API

All user routes require an active user and `discovery` scope. `admin` implies all scopes as before; v0.4 extends the auth scope vocabulary with `discovery`.

```text
GET  /api/me/discovery/search?q=&type=
GET  /api/me/discovery/catalog
POST /api/me/discovery/requests
GET  /api/me/discovery/requests
GET  /api/me/discovery/requests/{id}
POST /api/me/discovery/requests/{id}/cancel
GET  /api/me/discovery/subscriptions
POST /api/me/discovery/subscriptions/{id}/pause
POST /api/me/discovery/subscriptions/{id}/resume
```

`POST /api/me/discovery/requests` accepts only:

```json
{
  "tmdb_id": "123",
  "media_type": "movie",
  "tmdb_language": "zh-CN",
  "season_filter_json": null,
  "target_id": 1,
  "user_note": "please add the 2026 release"
}
```

Forbidden request fields include `owner_id`, `library_id`, `producer_profile_id`, `rule_profile_id`, `source_id`, `account_id`, `target_account`, `next_check_at`, `share_url`, `share_code`, `receive_code`, and `args`. If present, reject with 400 rather than silently accepting ambiguous input.

User responses are allowlisted DTOs:

- TMDB summary: title, year, media type, overview excerpt, poster path / safe image URL, local availability summary.
- Request summary: id, title snapshot, target label, status, safe reason, created/updated/reviewed times.
- Subscription summary: user status, canonical pipeline status, latest safe match/import state.

Never return raw TMDB JSON, `discovered_resources.share_code`, `receive_code`, `raw_text_ref`, `source_id`, producer profile config, rule JSON, account id, storage mount, job payload, stderr/stdout paths, raw debug, or stack traces.

### Admin API

Existing `/api/discovery/*` routes remain admin-only. v0.4 adds admin management routes inside the same admin boundary:

```text
GET  /api/discovery/requests?status=
GET  /api/discovery/requests/{id}
POST /api/discovery/requests/{id}/approve
POST /api/discovery/requests/{id}/reject

GET  /api/discovery/access-policies
POST /api/discovery/access-policies
PATCH /api/discovery/access-policies/{id}
GET  /api/discovery/access-policies/{id}/targets
POST /api/discovery/access-policies/{id}/targets
PATCH /api/discovery/access-policies/{id}/targets/{target_id}
```

Admin approve is the only path that maps a `pending_review` request to a canonical `discovery_subscriptions` row when policy mode is `approval_required`. `auto_approve` uses the same service path inside one transaction.

### UI

Current `/` remains Echo Admin. User-facing UI uses a separate shell:

```text
/app
/app/discover
/app/media/{media_type}/{tmdb_id}
/app/requests
/app/requests/{id}
/app/account
```

MVP UX:

- Work-focused search/request interface, not a marketing landing page.
- List-first layout with small fixed-ratio posters as supporting media.
- Clear states: logged out, disabled user, policy disabled, TMDB unavailable, no results, duplicate request, pending review, approved, importing, available, failed, canceled.
- User shell must not contain or htmx-load admin discovery controls.
- v0.4 MVP uses existing Bearer/API-token authentication for the first user app. Full username/password login and cookie sessions require a separate auth design; if cookies are introduced in a later version, CSRF protection is mandatory.

Frontend constraints:

- templ + htmx remains the default stack.
- Escape all user/TMDB/source text; do not use raw HTML/Markdown.
- Poster/image serving must reject SVG/HTML, use `X-Content-Type-Options: nosniff`, and have a no-poster fallback.
- Long titles and status labels must not overflow on 320px mobile or desktop.

## 5. 状态机

### Policy resolution

1. Load active user.
2. Find enabled `discovery_access_policies` ordered by priority where `subject_user_id = user.id` or `subject_user_id IS NULL`.
3. For search, enforce `can_search`; no enabled policy means search is forbidden.
4. For request creation, pick an enabled target matching requested `media_type`.
5. Enforce pending count, active subscription count, and cooldown.
6. If no target matches for request creation, fail closed.

### Request creation

```text
disabled          -> 403, no row
approval_required -> create pending_review
auto_approve      -> create approved + create/reuse canonical subscription
```

Request creation snapshots TMDB summary and target/profile names. It never creates producer jobs directly.

### Approval

`pending_review -> approved` transaction:

1. Re-read request with write lock.
2. Verify policy target, library, producer profile, and rule profile are still enabled.
3. Verify requester still has access or `grant_playback_on_approval=1` is allowed.
4. Create or reuse canonical `discovery_subscriptions` using `pipeline_owner_id`.
5. Create or update `user_media_subscriptions`.
6. Set `request.subscription_id`, `reviewed_by`, `reviewed_at`, status `approved`.
7. Insert request event.

Concurrent approve must return the existing approved result and must not create a second subscription or second dispatch path.

`pending_review -> rejected` records admin note and event, but never touches discovery scheduler.

`pending_review -> canceled` is allowed for requester or admin. Approved requests cannot be canceled retroactively; users cancel/pause their `user_media_subscriptions` instead.

### Scheduler integration

Existing v0.3 scheduler continues to process `discovery_subscriptions.status='active'`. v0.4 does not add new job kinds for discovery execution.

`discovery_policy_targets.match_mode` controls default decision behavior:

- `admin_review`: matches stay in review/queue states until admin uses existing match controls.
- `auto_dispatch`: accepted matches may follow existing v0.3 dispatch path, subject to rule score and producer validation.

User status is a projection. Users cannot call accept/reject/retry on matches.

## 6. Security

Hard boundaries:

- `/api/discovery/sources`, `/producer-profiles`, `/rule-profiles`, `/candidates`, `/matches`, `/run`, `/debug` remain admin-only.
- `/ui/discovery/*` remains admin-only.
- User-side routes are owner-scoped; no `?user_id=` override for non-admin.
- `HX-Request` is not an auth or CSRF boundary.
- Discovery user APIs cannot expose raw discovery data or producer internals.

Redaction must cover:

- `share_code`
- `receive_code`
- `share_url` password/query parameters
- `secret_ref`
- Telegram session paths
- TMDB/API keys
- producer args / job payload / stderr/stdout paths
- raw debug refs and raw text

Rate limits:

- Per-user and per-IP limits for TMDB search, request create/cancel, subscription pause/resume, and status polling.
- Global TMDB request/cache refresh limits.
- Hard caps for query length, note length, JSON body size, page size, and date/season filter complexity.

Audit events:

- user request create/cancel
- policy deny / rate-limit deny
- admin approve/reject
- user subscription pause/resume
- raw debug access (existing v0.3)

Audit rows store actor, target, from/to status, safe reason, request id, and time. They must not store sensitive raw source data.

## 7. 错误处理

User-facing errors are intentionally coarse:

| Condition | User response | Admin detail |
|---|---|---|
| No policy / policy disabled | 403 `request-disabled` | policy id / reason in audit |
| TMDB unavailable | 503 `metadata-unavailable` | TMDB error class |
| Duplicate request | 200 existing request summary | idempotency key match |
| Pending limit reached | 429 `request-limit-reached` | policy counters |
| Approval profile disabled | request `failed` or stays pending | profile/rule/library detail |
| Discovery/producer failed later | safe failed/importing status | existing match/job detail admin-only |

Do not expose stack traces, raw sidecar errors, producer stderr, share metadata, or account/storage details to users.

## 8. Testing

### Unit tests

- policy resolution priority, disabled/default policies, target media type filters.
- request validation rejects forbidden fields.
- idempotency key normalization, including TV season filter normalization.
- request state transitions and event append.
- canonical subscription reuse across two users requesting the same title.
- safe DTO serialization excludes sensitive fields.
- scope checks: `discovery` required for user routes; `admin` required for admin routes.

### HTTP/UI tests

- non-admin access to existing `/api/discovery/*` admin routes remains 403.
- user cannot access another user's requests/subscriptions.
- user cannot pass `owner_id`, profile ids, source ids, account ids, share args.
- user UI does not include admin discovery htmx endpoints or raw data.
- hostile TMDB title, user note, poster URL, and source-derived text are escaped.
- rate-limit and body-size failures are safe and logged without sensitive fields.

### Fake full-path integration

1. Seed users, policy, target, TMDB fake, library, producer profile, rule profile.
2. User searches TMDB and creates a request.
3. Another user creates the same request.
4. Admin approves once, and concurrent approve/retry returns the existing result.
5. Exactly one canonical `discovery_subscriptions` row exists.
6. Existing v0.3 fake discovery path creates a match and one `ingest_producer` job.
7. User request/subscription status projects imported/failed state without sensitive fields.
8. Non-admin access to source/profile/raw/debug/match controls remains denied.

### Real / operator gates

- Keep v0.2 real Emby gate passing.
- Keep v0.3 real 115 discovery/ingest gate passing.
- Add an environment-gated operator gate: real TMDB search/cache -> user request -> admin approve -> existing discovery dispatch path. Logs and responses must not contain share/receive/secret/producer args.

Telegram login/session authorization remains an operator-controlled non-blocking gate exactly as v0.3.

## 9. Deferred

- by-echo path restore/stream.
- hash conflict merge.
- WebDAV/S3 `.echo` output.
- 139 remote CAS tree import and 139/189pc automatic producer.
- full username/password web login, cookie sessions, and password reset flows.
- rich poster wall/trending/recommendations/social features.
- WebSocket notifications or push notifications.
- complex ACL beyond existing owner + `library_grants(permission='playback')`.

## 10. Final design decisions

- v0.4 is a user media request/admission layer above v0.3 discovery, not a new execution plane.
- Existing v0.3 discovery admin routes remain admin-only.
- Ordinary users create requests, not pipeline subscriptions or producer jobs.
- Canonical `discovery_subscriptions` are created/reused only by admin approve or policy auto-approve service logic.
- Multiple users requesting the same media target dedupe to one canonical pipeline subscription.
- User-visible status is a redacted projection, not direct exposure of discovery tables.
- `discovery` becomes a first-class API token scope.
- v0.4 does not expand provider dispatch beyond v0.3's 115-only automatic producer gate.
